# TiDB Cloud Health Inspection

## What it does

Runs a deterministic health inspection over a chosen time window and produces a
**customer report** plus internal evidence.

- **Scope**: one cluster, or a whole organization (screen every cluster and
  aggregate).
- **Plan is auto-detected.** Starter/Essential/Premium are checked with tenant-safe
  logical signals; Dedicated/BYOC add full-stack component and infrastructure
  signals, so their report is **fuller** — but *every* plan gets a customer report.
- Python performs every measurement, threshold decision, and status. Your job is to
  run it, decide which flagged items deserve deeper interpretation, and deliver the
  report — **not** to recompute or override any status or number.
- Overall status is `HEALTHY` / `NOTICE` / `WARNING` / `CRITICAL` / `N/A`, with a
  `confidence` of `HIGH` / `MEDIUM` / `LOW`.

You need a `CLINIC_API_KEY` in the environment or `.env` (see `config/env.example`).

## Inspect one cluster

`scripts/health_inspection.py` is the only entry point:

```bash
python3 scripts/health_inspection.py inspect \
  --cluster-id "<cluster_id>" \
  --relative-window 7d \
  --output-dir "./output/<cluster_id>"
```

Use an explicit window with `--start <ISO-8601> --end <ISO-8601>` instead. Provide
exactly one of: `--start`+`--end`, `--relative-window`, or `--relative-window`+`--end`.

The shared-plan customer report is **Chinese by default**; pass `--lang en` for
English. The runner also collects the equal-duration **previous window** so the
report shows 本周期 / 上周期 / 趋势.

## Inspect a whole organization

Screen every cluster in an organization with one command:

```bash
python3 scripts/health_inspection.py inspect-org \
  --org-id "<org_id>" \
  --relative-window 7d \
  --output-dir "./output/<org_id>"
```

Pass explicit clusters instead with repeated/comma-separated `--cluster-id a --cluster-id b`
(no `--org-id` needed). Each cluster is inspected into its own subfolder; a failed
cluster is isolated (recorded, the rest continue). The run writes `org-report.md`
(statuses aggregated, most severe first) and `org-summary.json`. This is the
lightweight organization screening path — see
[`references/organization-workflow.md`](references/organization-workflow.md).

## Reading the result

Each run writes, under `--output-dir`:

- `health-report.md` — **the customer report, for every plan.** Share this one.
  **All plans share one dynamically-numbered skeleton**, Chinese by default
  (`--lang en` for English):
  执行摘要 → 基础信息与基线 → 工作负载健康 → 资源健康 → 关键指标趋势 →
  SQL 分析 → 发现与优先建议 → 巡检覆盖. Shared plans (Starter/Essential/Premium)
  run on a shared resource pool, so **可靠性** and **配置与功能特性** are omitted
  (7 sections); Dedicated/BYOC add those two (9 sections). Every report shows
  本周期 / 上周期 / 趋势, the customer's **own** SQL Top-N (by digest), and the
  **关键指标趋势** section embeds current-vs-previous comparison charts
  (`charts/*.png`, generated by `report_charts.py`; skipped if matplotlib is absent).
  Deterministic Python owns every number and status; the LLM fills only the narrative
  slots (执行摘要 / 关键风险 / 优先建议) via `payload["interpretations"]` — see
  "Choosing what to deep-analyze". Deliver with the global `lark-cli` (see below).
- `charts/*.png` — the trend-comparison images the report references.
- `handoff.json` — the deep-analysis handoff (routed flagged checks); see
  "Division of labor" below.
- `normalized.json`, `gate.json`, `artifacts/`, `state/` — internal evidence,
  check-by-check results, and run state.

Rules of interpretation:

- `N/A` means "no usable signal" (missing, empty, unauthorized, or not yet
  supported). It is **never** Healthy, and never shown as zero.
- Never change the statuses or numbers Python produced.

## Division of labor: this skill collects + reports; deep analysis is delegated

This skill is the **deterministic collector + customer report**. Per-component deep
analysis (TiDB / TiKV / PD / TiCDC root-cause, sustained-window, hotspots) is **not**
done here — it is delegated to the external **o11y instance-inspection skill**, which
the orchestrating agent loads and runs. The two share the Clinic data layer.

### The handoff contract

Every run writes **`handoff.json`** (also embedded in `normalized.json` as
`handoff`) — the routable contract the orchestrating agent consumes:

```json
{ "deep_analysis": "delegated",
  "cluster_id", "cluster_name", "plan", "window",
  "items": [ {"check_id", "component", "severity", "signal"} ] }
```

- `items` are the `WARNING`/`CRITICAL` checks (same set as `analysis_candidates`).
- `component` (TiDB / TiKV / PD / TiCDC / Workload / …, from the check-id prefix) is
  the **routing key**: the orchestrating agent loads that component's o11y deep module
  for this `cluster_id` + `window`. The contract carries no raw values or PromQL.
- `gate.json` still sets `notification_owner: agent` / `llm_required` /
  `analysis_reasons` as the strong "needs attention" signal.

### Orchestration loop

1. Run this skill → `health-report.md` (with pending `（待分析解读）` slots) +
   `handoff.json`.
2. For each handoff item, the orchestrating agent invokes the external o11y skill's
   matching component module on that cluster/window (deep root-cause).
3. Fold the deep findings back as the report's narrative via `payload["interpretations"]`
   and re-render (see above). Do not re-score here. For an owner-authorized deeper SQL
   dive that surfaces **normalized SQL text / execution users** (SQLD-08/09), redact
   as required.

**Inject the interpretation back into the report.** The narrative slots
(执行摘要 / 关键风险 / 优先建议, and dedicated 执行计划) are filled from
`payload["interpretations"]` — a `{slot: text}` map you author from **this run's**
data (do not reuse a prior run's text; its numbers drift). Re-render without
re-collecting:

```bash
python3 scripts/customer_report.py render \
  ./output/<dir>/normalized.json ./interpretations.json > ./output/<dir>/health-report.md
```

Slots left empty render an honest "（待分析解读）" placeholder — never fabricated prose.

## Deliver the report (Feishu / Lark)

`health-report.md` is the source of truth for delivery, published with the global
`lark-cli` as the user's own identity (markdown import embeds the `@./` local chart
PNGs directly — text + tables + charts go up in one call). The **destination is
configured**, not hard-coded, so the skill is portable across environments:

```bash
# Target lives in config/delivery.v1.json (type wiki|folder, org grouping, title
# template); the environment-specific root token comes from $FEISHU_PARENT_TOKEN.
python3 scripts/publish_report.py --report-dir ./output/<run_dir> --org <org> --dry-run
python3 scripts/publish_report.py --report-dir ./output/<run_dir> --org <org>   # publish
```

- `publish_report.py` reads the delivery config, rewrites chart refs to `@./…`,
  re-runs the privacy validator, then creates the doc under the configured parent
  (per-org container reused idempotently) via `lark-cli docs +create --as user`.
- Auth once: `lark-cli auth login` (the user completes OAuth in a browser; identity
  in the OS keychain). No Feishu secrets in `.env`; only `FEISHU_PARENT_TOKEN`.
- Publishing is outward-facing: **confirm the destination and get the user's
  go-ahead before publishing.** Use `--dry-run` to preview the target + title first.
- The raw one-liner still works for an ad-hoc target:
  `sed 's#](charts/#](@./output/<run_dir>/charts/#g' health-report.md | lark-cli docs +create --as user --doc-format markdown --title T --parent-token TOK --content -`
- `scripts/report_to_html.py` bundles the report into a self-contained HTML for a
  quick local preview when `lark-cli` is unavailable — not a publishing path.

## When something goes wrong

- **"cluster Plan could not be determined safely"** — the plan resolved to Unknown
  (default-deny). Re-check the cluster id and access; do not force a plan.
- **"CLINIC_API_KEY not set"** — set it in the environment or `.env`. Never hardcode
  it into files or reports.
- **Window error** — you passed zero, both, or a reversed range. Supply exactly one
  valid form (see above).
- **Non-zero exit / "artifact validation failed"** — the run wrote `failure.json` in
  the output dir; read it and report the real cause. A low-traffic cluster is
  reported as `N/A`, not a failure.
- **Many `N/A` rows** — expected: shared plans exclude physical checks, and some
  checks are not yet implemented. The report's coverage section lists what was and
  wasn't assessed.

## Design and internals

Categories, checks, thresholds, and routing live in **Python and config**, not in
this file:

- `config/checklist.v1.json` — what to check (plan applicability).
- `config/collection.v1.json` — how each check is collected.
- `config/rules.v1.json` — thresholds that turn a value into a status.

To understand or extend the design, read `README.md` (the full design document) and
`references/` — in particular `references/plan-checklist-matrix.md`.
